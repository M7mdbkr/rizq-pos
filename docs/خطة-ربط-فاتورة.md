# خطة ربط نظام رزق مع هيئة الزكاة والضريبة والجمارك (منصة فاتورة)

> هذا المستند هو المرجع التقني لإكمال «المرحلة الثانية» من الفوترة الإلكترونية.
> آخر تحديث: يوليو ٢٠٢٦.

---

## ١) وضع النظام الحالي

### ✅ منجز — المرحلة الأولى (مرحلة الإصدار)
- فاتورة ضريبية مبسطة إلكترونية بكل الحقول النظامية (الاسم، الرقم الضريبي، الوقت، تفصيل الضريبة).
- رمز **QR بصيغة TLV/Base64** بالحقول الخمسة المعتمدة (يظهر تلقائيًا عند إدخال الرقم الضريبي في الإعدادات).
- **ترقيم فواتير تسلسلي** لا يقبل الفجوات.

### ✅ منجز — أساسات المرحلة الثانية (داخل التطبيق)
- **UUID** فريد لكل فاتورة (`orders.uuid`).
- **عدّاد فواتير ICV** = رقم الفاتورة التسلسلي (`orders.invoice_no`).
- **سلسلة تجزئة ضد التلاعب**: كل فاتورة تحمل `prev_hash` (تجزئة الفاتورة السابقة — بنفس عرف الهيئة: أول فاتورة تسلسلها `base64(SHA-256("0"))`) و`invoice_hash` (SHA-256 للحقول الجوهرية + السابقة).
- **فحص سلامة**: زر «فحص سلامة الفواتير» في شاشة المحاسبة يمشي على السلسلة كاملة ويكشف أي تعديل بأثر رجعي (مُختبَر: تعديل فاتورة واحدة من ٤٤٩ كُشف فورًا برقمها).

> ملاحظة تقنية: تجزئة المرحلة الثانية الرسمية تُحسب على XML الموقّع — السلسلة الحالية هي دفتر النزاهة المحلي الذي سيُشتق منه ذلك على الخادم.

## ٢) ما الذي تتطلبه المرحلة الثانية (الربط الفعلي)

الربط = جعل كل فاتورة تمر بهذه الدورة:

```
فاتورة → XML (UBL 2.1) → توقيع تشفيري (ECDSA secp256k1) → 
API الهيئة: إبلاغ (مبسطة، خلال ٢٤ ساعة) أو اعتماد فوري (ضريبية B2B) → 
تخزين الرد + QR موسّع (٩ حقول تشمل التوقيع والمفتاح العام)
```

### المكوّنات المطلوبة
1. **خادم (Backend)** — إلزامي، لأن:
   - مفاتيح التوقيع الخاصة لا يجوز تخزينها في متصفح.
   - واجهات الهيئة لا تقبل الاتصال من متصفح مباشرة.
   - «وحدة إصدار الفواتير» (EGS) يجب أن تكون بيئة محكومة.
2. **الاعتماد (Onboarding) لكل منشأة/جهاز**:
   - توليد **CSR** بامتدادات الهيئة الخاصة (نوع الفاتورة، الرقم الضريبي، اسم الوحدة…).
   - إدخال **OTP** من بوابة فاتورة (fatoora.zatca.gov.sa) → الحصول على **CCSID** (شهادة الامتثال).
   - اجتياز فحوصات الامتثال (فواتير تجريبية) → **PCSID** (شهادة الإنتاج).
3. **مولّد XML** بمواصفة UBL 2.1 + قواعد الهيئة (مئات قواعد التحقق).
4. **بيئة التطوير (Sandbox)** متاحة للمطورين بدون حساب إنتاجي — نبدأ بها.

### ما أقدر أنفّذه أنا (البرمجة)
- بناء الخادم كاملًا (Node.js): CSR، التوقيع، XML، الربط بالـSandbox ثم الإنتاج، الأرشفة.
- تحويل التطبيق ليرسل كل فاتورة للخادم لحظيًا (مع طابور للعمل دون اتصال).

### ما يلزم منك (لا يمكن تجاوزه)
- **حساب بوابة فاتورة** للمنشأة (يتطلب تسجيلًا ضريبيًا فعّالًا) + إدخال OTP عند اعتماد كل وحدة.
- **استضافة** للخادم (Supabase/VPS — قرارك في المرحلة السحابية).

## ٣) البيع للشركات / النشر في المتاجر — البنية المطلوبة

لبيع النظام كمنتج، البنية تصبح **متعددة المستأجرين (Multi-tenant)**:

| العنصر | لكل عميل (مطعم/شركة) |
|---|---|
| الرقم الضريبي وبيانات المنشأة | خاصة به في حسابه |
| اعتماد فاتورة (CSR → CCSID → PCSID) | **وحدة مستقلة لكل عميل** — العميل يدخل OTP من بوابته هو |
| مفاتيح التوقيع | تُخزن مشفرة على الخادم، معزولة لكل مستأجر |
| الفواتير والتقارير | معزولة لكل مستأجر |

- **الخياران التجاريان**:
  1. **ربط مباشر** (نبنيه بأنفسنا): لا رسوم لكل فاتورة، تحكم كامل، لكن صيانة مواصفات الهيئة علينا. ← **الموصى به** لمنتج يُباع.
  2. **وسيط مرخّص** (مزودو حلول فوترة جاهزة عبر API): إطلاق أسرع، لكن تكلفة شهرية/لكل فاتورة وتبعية لطرف ثالث.
- **المتاجر (App Store / Play)**: تغليف الواجهة بـ Capacitor + حسابات المطور (Apple ‏٩٩$/سنة، Google ‏٢٥$ مرة واحدة) + سياسة خصوصية (نظام حماية البيانات الشخصية السعودي PDPL). النشر منطقي **بعد** جاهزية السحابة والربط، لأن المنتج التجاري بدونهما غير مكتمل.

## ٤) خارطة الطريق التنفيذية (بالترتيب)

1. **المرحلة السحابية** *(القرار المطلوب: حساب Supabase مجاني أو VPS)*
   - نقل قاعدة البيانات للخادم مع حسابات ومستأجرين + مزامنة لحظية.
2. **وحدة زاتكا على الخادم — Sandbox أولًا** *(لا تحتاج أي حساب رسمي)*
   - CSR + امتثال + إبلاغ فواتير تجريبية حتى تخضرّ كل الفحوصات.
3. **الإنتاج للمنشأة الأولى (مطعمك)** *(تحتاج: حساب بوابة فاتورة + OTP)*
4. **تعدد المستأجرين + لوحة إدارة العملاء** (للبيع للشركات).
5. **التغليف والنشر** (Capacitor + المتاجر + سياسة الخصوصية).
